# Shipping SafeStart to the Play Store

The site is now an installable PWA. This turns that into an Android app on the
Play Store, using a Trusted Web Activity: a real Android app whose whole window
is safestart.trust-raise.com with no address bar. Google supports this route
directly, which is why Android is the easy case and iOS is not.

**What this means in practice:** the app has no separate codebase. Fix a guide,
push, and the app shows the fix on next launch. No release, no review, no
waiting. The only things that ever need a new release are the icon, the name,
and the app metadata.

---

## What Dave has to do, and what can be automated

Three things need you specifically, because they involve a signing key and a
payment, and neither belongs anywhere near an automated tool.

1. **Create the signing key.** Lose it and the app can never be updated again
   under the same listing. There is no recovery.
2. **Pay the Play Console registration.** One-off, currently $25.
3. **Submit the release.**

Everything else is either already done or is a command you can paste.

---

## 1. Already done, in this repo

- `manifest.json`, generated by `scripts/build.js` so it cannot drift
- `sw.js`, built from `src/sw.js` with a content fingerprint
- Icons at 192, 512 and 512-maskable, generated by `scripts/icons.js` from the
  same shield the site uses in its header
- `.well-known/assetlinks.json`, with the fingerprint still to fill in
- Vercel headers so `sw.js` is never cached hard, `manifest.json` is served as
  `application/manifest+json`, and `assetlinks.json` as `application/json`
- `check.js` fails the build on a missing manifest field, a missing maskable
  icon, a lost cache fingerprint, or a worker that stops treating `/help/` as
  network-first
- `browser-test.js` installs the worker, goes offline, and proves every guide is
  still readable, then proves a crisis page online is fetched fresh

Run `node scripts/icons.js` only if the shield changes. It is not part of the
normal build.

## 2. Create the signing key

Somewhere outside this repo:

    keytool -genkeypair -v \
      -keystore safestart-upload.keystore \
      -alias safestart \
      -keyalg RSA -keysize 2048 -validity 10000

Back the file up somewhere that is not a git repo and not your laptop only. The
`.gitignore` already blocks `*.keystore`, `*.jks` and `*.p12`, but the real
protection is keeping it elsewhere.

## 3. Generate the Android project

Bubblewrap is Google's own tool for this.

    npm install -g @bubblewrap/cli
    mkdir ~/safestart-android && cd ~/safestart-android
    bubblewrap init --manifest https://safestart.trust-raise.com/manifest.json

It reads the live manifest, so deploy first. Answers worth getting right:

| Prompt | Answer |
|---|---|
| Application ID | `com.trustraise.safestart` |
| Display mode | `standalone` |
| Status bar colour | `#FBF0E9` |
| Signing key | point it at the keystore above |
| Include support for Play Billing | no |

Then build:

    bubblewrap build

That produces `app-release-bundle.aab` for Play, and an APK you can sideload to
test on a real phone first. Do test on a real phone: the emulator will not show
you the address-bar problem below.

## 4. The fingerprints, which is where this usually goes wrong

**Two** fingerprints need to end up in `.well-known/assetlinks.json`, and
missing the second one is the most common Trusted Web Activity mistake. The
symptom is an app that works but has a Chrome address bar pinned across the top,
which looks broken.

**Your upload key:**

    keytool -list -v -keystore safestart-upload.keystore -alias safestart

**Google's app signing key.** Play re-signs every release with a key Google
holds, so the fingerprint that reaches real phones is not yours. Play Console →
Release → Setup → App signing. This one only exists after your first upload, so
expect to come back and add it.

Put both in `sha256_cert_fingerprints` as colon-separated uppercase hex, then
push. `check.js` currently warns that the placeholder is still there, and that
warning turns into a pass once real fingerprints go in.

Verify with Google's checker:
https://developers.google.com/digital-asset-links/tools/generator

## 5. Play Console listing

Things they will ask for that are worth deciding now rather than at upload:

- **Category.** Parenting, or Education. Parenting is the better fit.
- **Content rating.** Answer the questionnaire honestly: no user-generated
  content, no ads, no purchases. It should come back as suitable for everyone.
- **Data safety form.** This is the one where SafeStart does well and it is
  worth being precise, because the answers are public on the listing. No
  account, no personal data collected, no data shared with third parties. The
  only thing to declare is the Vercel analytics, which is aggregate and is
  deliberately excluded from `/plan/` because that URL carries a child's age and
  app list.
- **Target audience.** Declare it as for adults, not children. It is a tool for
  parents. Declaring a child audience pulls you into Play's Families policy and
  a much heavier review, for no benefit.
- **Privacy policy URL.** Play requires one. There isn't one on the site yet.
  This is the one genuine blocker in this list.

---

## What is missing before you can submit

1. A privacy policy page. Play will not accept the listing without a URL.
2. The two fingerprints in `assetlinks.json`.
3. Feature graphic (1024x500) and at least two phone screenshots.

The privacy policy is the real work, and the site is in an unusually good
position to write a short honest one, since the answer to most of it is "we
don't".

---

## Worth knowing

**The address bar test.** Sideload the APK before submitting. If you see a
Chrome address bar, the fingerprints are wrong. Nothing else causes it.

**Updates.** Content changes need no release. Only the icon, name, or Android
config do.

**iOS is not this.** Apple's minimum-functionality rule exists to reject apps
that are a website in a shell. That would need a real argument, probably built
around offline and notifications, and it is a different project.
